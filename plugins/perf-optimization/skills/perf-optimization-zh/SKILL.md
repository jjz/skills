动手改之前先确认实际技术栈（框架、元框架版本、图片/CDN 管线、构建工具），不要凭假设——图片组件、脚本加载策略、字体加载器这些 API 的名字和默认行为在不同框架之间、甚至同一框架的不同大版本之间都会变，套用一个过时或跑错框架的 API 是"修完编译不过/悄悄不生效"的常见原因。如果仓库自己的文档/AGENTS.md/CLAUDE.md 里提到了框架版本相关的坑，先读那些。

**教训**：只检查"有没有用优化过的图片组件"这种表面检查，会漏掉两类更隐蔽但影响更大的问题——(a) 加载优先级提示（`priority`/`fetchpriority`/`preload`）标在了错误的图片上——一张不在首屏的图被标成高优先级，会和真正的 Hero 图抢加载优先级，两边都变慢；(b) 重量级库（富文本/Markdown 渲染器、轮播组件、图表库、代码高亮）在会打包进客户端的代码里被无条件引入，导致不需要它的页面也要下载它的 JS。以后每次审查都要过一遍下面全部类别，不要只抽查图片有没有用优化组件。

## 一、图片（对 LCP/带宽影响最大，优先查）

找出代码里所有图片标签/组件（`<img>`、框架自带的图片组件、CSS `background-image`），逐个检查：

1. **是否真的走了优化管线**（框架的图片组件、图片 CDN、构建期优化器），还是原生 `<img>`/CSS 背景直接指向一张原图？原生标签不是天然错误——一个小图标，或者图片来源域名优化器根本连不到，都是合理的例外——但这应该是刻意且有记录的例外，不是默认状态。先 grep 现有的"故意不优化"标记（注释、lint-disable），再决定要不要"修"它；不先解决根本原因（比如把域名加进图片白名单）就强行改掉，可能直接把构建改坏。
2. **优先级/预加载提示必须标在真正的 LCP 候选图上，不是"看起来重要"的那张。** 只有首屏最大的那张图（几乎总是 Hero 图）该标记优先/急切加载，其余图片都应该懒加载。判断依据是渲染顺序和视口内可见性，不是组件在源码里"看起来"有多显眼。一个真实反复出现的坑：页面靠下某个 section 的背景图被标成高优先级，抢走了真正 Hero 图的加载优先级，两边都变慢。轮播图/图片列表里，优先级提示只能加在第一张/当前激活的那张——绝不能在 `.map()`/循环里无条件全加，多个同时"最高优先级"等于没有优先级。
3. **响应式图片需要正确的 `sizes`（或等价属性），不能偷懒用默认值。** 图片跟随容器缩放时，`sizes` 该描述这张图在各个断点下**实际渲染的宽度**，不是原图尺寸。不要看到 class 里带"全宽"字样就反射性写 `sizes="100vw"`：要看最近的、真正限制最大宽度的祖先容器（居中的 `max-width: 880px` 外层、定宽卡片），描述的是**那个**容器的宽度。`sizes` 写错会导致浏览器请求的图片尺寸远大于实际渲染尺寸——用 DevTools 核对请求图片的尺寸和元素实际渲染框的大小，不要凭 class 名称猜。
4. **格式/质量设置**：优先用现代格式（AVIF/WebP），让优化器自动生成回退链，而不是手写多个 `<picture>` source；确认管线是否强制质量档白名单（有些框架/服务是），还是接受任意质量值。
5. **检查有没有从未真正经过优化器的超大源图**：只要都走优化管线，源图大小不等于用户实际下载的字节数，但两种情况仍然要查——(a) 一张巨大的源图被原生 `<img>`/CSS 背景引用，**这种情况会原样把全尺寸图发给用户**；(b) 静态资源目录里躺着一个完全没人引用的孤立大文件。搜索引用关系时，除了组件源码，也要搜内容/i18n/CMS 数据文件——图片路径经常是从数据（i18n JSON、CMS 字段）拼出来的，不是硬编码在模板里，只搜组件目录会漏掉这些。

## 二、三方脚本与嵌入内容

- 给每个三方脚本按"多快需要跑起来"分级，加载时机不早于这个需求：不阻塞渲染的统计/广告脚本 → 页面可交互之后再加载；客服插件、社媒嵌入这类首屏不需要的 → 懒加载/空闲时加载/交互时才加载；只有真正必须阻塞渲染的（cookie 同意弹窗、必须最早跑的机器人/风控检测）才用同步/尽早加载，且这类脚本数量和体积都要尽量压到最小。
- 任何用来决定渲染内容或做个性化的外部数据请求（地理位置、同意状态、A/B 分组）都应该异步且不阻塞首屏渲染——放在 effect/挂载之后发起，不要在渲染页面骨架之前 await 它。
- 如果许可/服务条款允许、且厂商不要求走它自己的 CDN 才能自动更新，优先自托管三方脚本——省掉一次 DNS 查询+连接，还能纳入本站自己的缓存策略。否则至少对确定会用到的三方域名加 `preconnect`/`dns-prefetch`。

## 三、JS 包体积 / 代码分割

- 对每个重量级依赖（富文本/Markdown 渲染器、轮播库、图表/动画库、代码高亮、PDF/文档预览）grep 它真实的引入位置——依赖清单里有但代码里零引用的话不会打进产物（tree-shaking 会处理），但值得在报告里指出这可能是遗留/半成品代码；**不要擅自删依赖或删用到它的组件**，可能是刻意留着近期要用的。
- **代码是在服务端执行还是发到客户端，通常是比手动代码分割杠杆更大的优化点。** 在有服务端/客户端组件区分的框架里（React Server Components、Astro islands、Vue 服务端组件等）：一个只在纯服务端渲染组件里用到的重量级库，只要这个组件树保持纯服务端渲染，成本是零。而只要这整棵子树被某个客户端边界组件渲染——哪怕用到重库的那个组件本身没标客户端指令——底下所有东西都会被打进客户端产物。所以：先判断这个客户端边界是不是真的必要（有没有真实的事件处理/hook/浏览器 API）——如果不需要，去掉它比任何下游优化都更彻底。如果客户端边界确实无法去掉（比如为了避免多断点下的 hydration/布局不一致），但组件内部只有**部分分支**才需要重量级库，就只把那个 import 包进框架提供的动态/懒加载原语，让不走这条分支的页面/分支不用下载它。需要被搜索引擎/AI 问答引擎抓取的内容要保持服务端渲染（参见 seo-geo 技能）——为了省客户端字节而关掉 SSR，是拿可索引性换包体积，通常不划算。
- 在没有 SSR/CSR 区分的框架里（纯 SPA、原生 JS 的静态站点），等价的优化手段是按路由或按交互做代码分割（在路由切换或用户操作时才动态 `import()`），而不是全部打进一个入口包。

## 四、字体

- 自托管字体（或用框架自带的字体加载原语，通常会自动自托管），不要手写 `<link>`/`@import` 指向外部字体服务——省掉一次额外的跨域连接，还能让字体走和站点其余资源一样的缓存/CDN 策略。
- 留意同一份字体被从两个地方重复加载（比如某次重构后 layout 文件其实不再真正渲染 `<html>`/`<body>`，但里面遗留的一次字体加载调用没删）——每次改动 layout/模板嵌套结构时都会反复出现的一类真实 bug。改完 layout 结构后，grep 一遍代码里所有字体加载调用。
- 格式支持的话，优先用可变字体（variable font），不要给每个字重单独发一份文件。
- 设置 `font-display: swap`（或加载器的等价选项），让文字先用回退字体立即显示，不要在自定义字体下载完之前一直不可见；大多数现代字体加载工具默认已经是这样——去确认，不要想当然。
- 工具链支持的话，对字体做子集化，只保留实际用到的字符集（对 CJK 字体尤其重要，不做子集化的话体积会非常大）。

## 五、CSS 与阻塞渲染的资源

- 如果构建工具/框架能按路由或按组件生成样式，就不要把一份庞大的整体 CSS 发给每个页面——页面上用不到的 CSS，浏览器照样要付下载和解析的成本。
- 构建工具支持内联的话，首屏关键 CSS 应该不用等一次阻塞性的网络请求就能拿到；非关键 CSS 可以异步加载。
- 给所有异步加载、且有确定尺寸的内容（图片、广告、嵌入内容、Web 字体）预留布局空间——这是 CLS 劣化最直接、最常见的成因。给元素显式写 `width`/`height`（或 `aspect-ratio`）比事后用 CSS 补救更可靠。

## 六、缓存与分发

- 静态资源（图片、字体、带哈希的 JS/CSS 产物）应该带长期、不可变的缓存头（`Cache-Control: public, max-age=31536000, immutable`）——因为内容变化时构建工具会连带改文件名哈希，所以这样做是安全的。
- HTML/API 响应的缓存策略要按内容实际的更新频率刻意设置——不要让框架的默认行为悄悄缓存了本该保持新鲜的内容，也不要让本该被缓存的内容完全没有缓存头。
- 确认压缩在生产环境里真的生效（优先 Brotli，回退 gzip)——去查生产环境的响应头，不要只信托管平台"声称"支持。
- 条件允许的话，静态资源和图片走 CDN/边缘网络分发，这样往返时延不会随访客离源站服务器的距离线性变差。

## 七、移动端

把移动端当成默认目标去优化，不要留到最后才顺带看一眼——大多数网站的真实流量和 Core Web Vitals 现场数据主要来自移动端，而且移动端环境更苛刻（CPU 更慢、网络更慢/按流量计费），一个在移动端够快的页面在其他设备上通常也够快，反过来不成立。

- **PageSpeed Insights/CrUX 的现场数据默认以移动端为主**，Lighthouse 的默认移动 profile 同时开了 CPU 和网络节流——只跑桌面版 Lighthouse，可能看到一个轻松达标的 LCP/INP，但完全不反映大多数真实访客的体验。永远要跑（并且汇报）移动 profile 的结果，不能只看桌面版。
- **移动端 CPU 的主线程吞吐量通常比开发者的笔记本慢 4-6 倍**，这就是为什么在桌面不开节流跑分析时看起来无害的重 JS，到中端手机上就会击穿 INP 预算。要开 CPU 节流去分析（Chrome DevTools 的 "4x slowdown"/"6x slowdown"，或 Lighthouse 的移动 preset），不能只看不节流的结果。
- **`<meta name="viewport" content="width=device-width, initial-scale=1">` 必须存在且写对**——viewport 标签缺失或写错，会让移动端浏览器按桌面宽度渲染整页再整体缩小，不仅显示效果是坏的，还会让 CLS/LCP 的测量结果失真（或者被严重劣化）。这是每个项目该查一次的基础项，尤其是任何不是由框架自动生成的自定义 HTML 外壳。
- **响应式图片的断点（第一节第 3 条）要真正覆盖移动端视口宽度**，不能只是一个在桌面宽度下"算出来碰巧对"的 `sizes` 字符串——确认生成的 `srcset` 里有足够小的候选图，别让窄屏手机在慢网络下下载了桌面尺寸的图。
- **移动端的页面体积预算比"办公室 wifi 下感觉快不快"更严格**——按流量计费/信号差的移动网络下，JS/图片/字体每多出的一点体积都会变成能被用户感知的真实延迟；拿不准要不要懒加载/延迟加载某个东西时，按移动端场景去判断。
- **移动端的 INP 主要由触摸/点击响应速度决定**，不是 hover 状态（触屏设备大多数根本没有 hover）——审查 tap/click 事件处理函数里有没有同步的重计算（大范围 state 重算、没做节流的重渲染），不要以为桌面端的 hover 交互分析已经覆盖了这块。

## 八、验证

不要看着 diff 觉得"应该更快了"就算完事。用生产构建在本地或真实的部署预览环境里跑起来（开发模式服务器的性能特征和生产环境不一样，通常更差也不具代表性），然后：

- 对生产构建跑 Lighthouse/PageSpeed Insights，**优先用移动端设备/节流 profile 作为主要判断依据**（参见第七节），改动前后直接对比 LCP/CLS/INP——不要只看总分，总分可能把某项指标的劣化被另一项的改善抵消掉。如果桌面流量占比也不小，桌面 profile 也要跑，但不能拿"桌面达标"顶替移动端检查。
- 用浏览器 DevTools 的 Performance/Network 面板（开启移动端 CPU/网络节流）确认到底哪个资源是真正的 LCP 元素、它什么时候开始/结束加载，尤其是改动了 Hero 图/首屏内容之后。
- 实验室数据（Lighthouse）和现场数据（真实用户的 Core Web Vitals，比如 CrUX、PageSpeed Insights 的 Field Data 部分，或者站点已经接入的 RUM 工具）可能会不一致——判断真实用户是否真的受影响时以现场数据为准，只有实验室数据变好但没有现场数据印证时要保持怀疑。如果现场数据有设备细分，记得单独查看——一个只在移动端出现的劣化，可能被桌面端的改善抵消，藏在"全设备"汇总数字里看不出来。
- 如果改动涉及在不同断点/客户端-服务端边界下渲染方式不同的内容，还要确认渲染出的 HTML 里没有引入重复内容（参见 seo-geo 技能第 6/7 节)——"修" layout-shift 或 hydration 问题时把某段内容渲染两份、靠 CSS 切换可见性，是这类问题的常见诱因。
