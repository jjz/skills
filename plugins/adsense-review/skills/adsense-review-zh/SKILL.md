# AdSense 合作规范审查

*[English version →](../adsense-review/SKILL.md)*

权威来源（条目原文以这几页为准，政策会更新，不要凭记忆）：
[Program policies](https://support.google.com/adsense/answer/48182) ·
[Behavioral policies](https://support.google.com/adsense/answer/2753860) ·
[Publisher Policies 详细分类](https://support.google.com/adsense/answer/10502938) ·
[新手指南](https://support.google.com/adsense/answer/23921) ·
[EU 用户意见征求政策](https://support.google.com/adsense/answer/7670013) ·
[EEA/UK/瑞士同意管理要求](https://support.google.com/adsense/answer/13554116)

**三个常见盲区**（审查"还没准备好"的常见原因）：
1. **CMP 与隐私政策文字是两回事**：很容易只查"隐私政策页面文字写了什么"就以为查完了，从而完全漏掉 CMP/EU 用户同意政策这整个类别。隐私政策的文字披露只是众多 Publisher Policies 要求中的一项；真正**部署**同意管理平台是 EU 用户同意政策下另一条独立的、可单独触发违规的强制要求，光有文字完全不满足它。
2. **薄页/低价值内容**（ADS-CONTENT-03）：现实中最常见的拒审原因。一个站在政策上完全干净（无盗版、无仇恨、无成人内容），仍可能因为页面太浅、太模板化、数量太少而被拒。字数本身不是标准——全是"上传→点击→下载"的套话、没有独立有用信息的页面，即使 400 词也算薄页。审查时一定要衡量并指出内容深度，而不只是内容合法性。
3. **缺少信任页**（ADS-UX-05）：About、Contact、隐私政策（必要时含条款）是审核员判断可信度的第一眼。"有隐私政策"还不够——如果没有 About 页、没有可用的联系方式、页脚也没有任何指向它们的链接，就是明显的信任短板。

## 输出格式
按严重程度输出——**Blocker → High → Medium**——然后输出完整检查表，再输出一份"需要账号持有人确认"的清单。每项发现都要给出具体的规范 ID + 证据（文件/URL/截图）。使用下面的 ID，便于对照政策核对：

- **ADS-ELIG** 资格；**ADS-OWN** 所有权；**ADS-SITE** 站点列表；**ADS-TXT** ads.txt；**ADS-CONTENT** 内容；**ADS-UX** 信任/体验；**ADS-CRAWL** 可抓取性；**ADS-PROG** 计划/行为；**ADS-PUB** 发布商；**ADS-REST** 受限内容；**ADS-PRIV** 隐私。
- 只有账号持有人才能核实的项，一律标 **Unknown / 自查**——永远不要把"代码里查不到"当成"已合规"或"不适用"。

## 检查表（逐条核对，不要只抽查其中几条）

### 一、资格与所有权（多为账号层面自查）
- **ADS-ELIG-01** 申请人年满 18 岁（或由监护人代管账号）。工具无法核实，需问站长。
- **ADS-ELIG-02** 同一发布商不重复注册 AdSense 账号。加新站应放在现有账号里，重复开户会被封。自查。
- **ADS-ELIG-03** 内容整体符合计划政策与发布商政策（总闸——下面各项干净才算过）。
- **ADS-ELIG-04** 托管平台（Blogger/YouTube）走托管账号流程；自有域名站点不适用。
- **ADS-OWN-01** 能向页面 `<head>` 注入代码（有源码/CMS 权限；建站平台需确认支持自定义代码）。自查。
- **ADS-OWN-02** 域名在本人名下、DNS 可自主管理。不要拿不属于自己的站申请。自查。
- **ADS-OWN-03** 页面 JS 正常渲染、HTML 结构完整（抓真实 HTML 验证）。

### 二、站点与技术
- **ADS-SITE-01** 站点已加入 AdSense「网站」列表并通过审核。只能后台操作。自查。
- **ADS-SITE-02** 至少一种所有权验证方式可部署（代码/ads.txt/meta）。自查。
- **ADS-TXT-01** 若存在 `ads.txt`，须包含 Google 授权行。
- **ADS-TXT-02** 已发布 `ads.txt`（建议，防广告库存被冒卖）。
- **ADS-CRAWL-01** 站点在线，关键页返回真实 HTTP 200（首页与抽样页无 404/5xx）。
- **ADS-CRAWL-02** `robots.txt` 不拦截 Google/AdSense 爬虫；内容页无登录墙。
- **ADS-CRAWL-03** 页面 GET 可达（不依赖 POST）。
- **ADS-CRAWL-04** 无过多或脆弱的跳转链。
- **ADS-CRAWL-05** URL 稳定简洁（无会话 ID 等一次性参数）。
- **ADS-CRAWL-06** DNS/TLS/主机响应稳定；HTTPS 正常。
- **ADS-CRAWL-07** 有 sitemap 与稳定收录路径。

### 三、内容——原创性 AND 深度
- **ADS-CONTENT-01** 内容原创、有用、对访客有价值（无采集/AI 洗稿/占位内容）。
- **ADS-CONTENT-02** 不纯靠转载/嵌入视频/联盟 feed，有原创观点或数据。
- **ADS-CONTENT-03** **主体内容量充足，无大量薄页。** 这是头号拒审原因。抽样页应各自有真正独立、有用的信息——不能是几十页共用同一套"How to use"骨架。见下方「内容深度整改」。
- **ADS-CONTENT-04** 不处于建设中/空壳状态（检查占位日期、"coming soon"、lorem ipsum、导航里 404 的链接）。
- **ADS-CONTENT-05** 广告/联盟/推广内容不超过自有内容。
- **ADS-CONTENT-06** 主要内容语言在 AdSense 支持范围内。
- **ADS-CONTENT-07** 评论区与 UGC 有审核，无垃圾/违规内容。
- **ADS-CONTENT-08** 无关键词堆砌与门页（doorway pages）。
- **可信度信号**（属于 CONTENT-04/05 的一部分）：帖子无未来日期/占位日期、无半成品页面、无"About 找不到"、无隐瞒身份。

### 四、信任与体验
- **ADS-UX-01** 导航清晰可用。
- **ADS-UX-02** 用户能看懂网站是做什么的、能顺畅找到内容。
- **ADS-UX-03** 无诱导性导航：假下载按钮、无关跳转、指向不存在内容的链接。
- **ADS-UX-04** 无恶意行为：强制跳转、自动下载、弹窗弹底、篡改用户设置。
- **ADS-UX-05** **信任页存在且放进页脚导航**：About、Contact、隐私政策（必要时含条款）。有隐私政策但没有 About 页或联系渠道，是可信度问题，不能算通过。
- **ADS-UX-06** 无「广告位优先」的混淆布局（广告在前、内容被埋没）。

### 五、行为 / 计划
- **ADS-PROG-01** 不自点广告、不刷展示/点击。行为红线；自查。
- **ADS-PROG-02** 不引导用户点广告（无「点击支持我们」/指向广告的箭头）。
- **ADS-PROG-03** 广告与内容区分清楚，标签中性（如 Ad/Sponsored）。
- **ADS-PROG-04** 流量来源合法（无 PTC/互点/垃圾邮件/垃圾评论引流）。自查。
- **ADS-PROG-05** 不修改广告代码以夸大效果；原样粘贴官方代码。
- **ADS-PROG-06** 广告只放在正常内容页（不放软件/弹窗/邮件/空页面）。自查。
- **ADS-PROG-07** WebView 变现要求（普通网站不适用）。
- **ADS-PUB-01** 无违法内容或违法活动引导。
- **ADS-PUB-02** 无侵权/盗版/假冒品牌内容。
- **ADS-PUB-03** 无仇恨/骚扰/自残鼓动/暴力美化。
- **ADS-PUB-04** 无虐待动物或濒危物种制品。
- **ADS-PUB-05** 不隐瞒或虚报网站身份/内容目的/从属关系。
- **ADS-PUB-06** 无钓鱼/骗个人信息/虚假暴富承诺。
- **ADS-PUB-07** 无造假文书/代考/破解/间谍软件等「助不诚信」内容。见下方安全工具说明。
- **ADS-PUB-08** 无性交易/跨国婚介/面向家庭内容夹带成人主题。
- **ADS-PUB-09** 发布商信息与广告请求数据真实完整（ads.txt 与身份一致）。
- **ADS-PUB-10** 广告不遮挡内容/导航，不设点广告才能离开的死屏。
- **ADS-PUB-11** 不在无内容/低价值/建设中/纯转载页面放广告。
- **ADS-PUB-12** 广告不脱离上下文出现（后台页/屏幕外）。
- **ADS-PUB-13** 无破坏选举/违背科学共识的健康或气候虚假声明。
- **ADS-PUB-14** 无在公共议题上欺骗用户的合成/篡改媒体。
- **ADS-PUB-15** 无任何危害儿童的内容（一票否决）。
- **ADS-PUB-16** 敏感事件（灾难/危机）内容不消费、不冒犯。

### 六、受限内容（每项都要明确判过，不能想当然）
- **ADS-REST-01** 露骨色情内容/成人用品/成人向保健品。
- **ADS-REST-02** 血腥惊悚/粗俗语言占显著位置。
- **ADS-REST-03** 枪支武器及制造改装教程。
- **ADS-REST-04** 烟草/娱乐性药物及吸食教程。
- **ADS-REST-05** 酒类在线销售或鼓励酗酒。
- **ADS-REST-06** 在线赌博/付费碰运气游戏。
- **ADS-REST-07** 处方药销售/网上药房/未批准药品保健品。
- **ADS-REST-08** 广告遮挡类实现（贴片/悬浮视频违规）。

### 七、隐私
- **ADS-PRIV-01** 发布隐私政策，披露 Cookie 等数据收集与使用。
- **ADS-PRIV-02** 隐私政策说明第三方（广告商）会使用 Cookie/标识符。
- **ADS-PRIV-03** 不在广告请求中传个人身份信息（PII，URL 参数/数据层不能带邮箱手机号等）。接广告代码时自查。
- **ADS-PRIV-04** EEA/UK/瑞士流量需部署经认证的 CMP/同意横幅（见下方 CMP 详解）。
- **ADS-PRIV-05** 收集精确位置数据须先告知并取得同意；不收集定位则不适用。
- **ADS-PRIV-06** 儿童导向内容须标记并禁用兴趣定向（账号级开关 + 隐私政策声明）。
- **ADS-PRIV-07** 不在 google.com 域名上设置/篡改 Cookie（仅自写广告代理/注入才可能触发）。
- **ADS-PRIV-08** 不用敏感信息（健康/宗教/性取向等）做定向或建受众。
- **ADS-PRIV-09** 美加地区房产/招聘/信贷广告不得按人群属性定向。
- **ADS-PRIV-10** 使用个性化广告须有数据使用权与利益相关广告（IBA）披露。

## 内容深度整改（工具/功能类网站的 Blocker 级问题）
大量结构完全相同的「工具」「生成器」页面是典型的低价值/门页模式。申请前先改：
- **让每个页面都可区分**：把每个页面重写成独立、有信息增量的指南，而不是共用同一套模板。分别写清适用场景、处理逻辑、参数含义、限制条件、隐私处理方式和真实案例——每个页面要不一样。
- **字数目标**：内容页正文 800–1500 词，配结构化小标题。242 词的 `/help` 或 460 词的工具页过不了深度门槛。
- **去掉重复的"How to use"模板**：不要跨页逐字复用同一套步骤。
- **扩充内容资产**：纯工具站要增加真正的文章（指南、"底层原理"、排障）并互相内链；sitemap 里 95% 是工具 URL 会被当成门页集合。
- **增加信任/透明内容**：一个有真实运营者/历史的 About 页 + 一篇"你的文件如何被处理/数据生命周期"说明页——这是工具站最有价值的信任信号。

## 安全类工具——「助不诚信」边界（ADS-PUB-07）
「移除密码」「移除证书签名」「清理/sanitize」「解锁」这类工具本身有合法用途，但正好踩在政策线上。除非每个页面都明确写出合法使用边界，否则会被读作"协助绕过权限保护"。在这些页面加醒目声明，例如：
> "本工具仅用于你有权处理的文件（你自己创建的文件，或文件所有者已授权你修改的文件）。请勿用它绕过你无权移除的权限保护。"

对工具站来说，这能同时显著降低拒审风险和误用风险。

## CMP / EU 用户同意政策详解
- 是否**实际部署**了经 Google 认证且集成 IAB Europe TCF 的 CMP（Google 自家的 CMP 现在整合进了 AdSense 后台"隐私权和内容/Privacy & messaging"页签，或用 Cookiebot/OneTrust/Quantcast Choice 等第三方）——光有隐私政策文字、没有真正的同意弹窗/同意信号传递，就是不合规。
- 不满足要求的后果不是"不能投放广告"，而是该地区流量只能展示**非个性化/受限广告**，收入下降；Google 的自动化审查仍可能把"未检测到 CMP"列为需要处理的问题项，即便广告本身照常在跑。
- CMP 的实际启用（后台生成消息、拿到具体脚本参数）是 **AdSense 账号后台操作**，不是纯代码能完成的——代码这边只能预留好脚本插入点，不要凭空编造脚本内容（脚本 URL 里的参数是按账号生成的，编错了等于挂了个假同意弹窗，比没有更糟）。
- CMP 是怎么运作的（避免误解成"每次都要用户手动点同意才能用网站"）：
  - **按访客地区触发**：CMP 通常先判断访客是否在 EEA/英国/瑞士（一般靠 IP 地理位置），只对这些地区的访客弹同意横幅，其他地区默认走个性化广告流程，不弹窗。
  - **同意状态只问一次，存本地**：用户选择后写入 cookie/localStorage 里的 TC String（IAB TCF 标准编码），下次访问同一浏览器不会重复弹，除非同意过期或消息内容变更。
  - **拒绝/未同意 ≠ 网站坏了**：后果只是这次访问只能投放非个性化广告，页面其他功能、必要 Cookie 都照常工作。真正会被判定违规的是"压根没有征求机制"，不是"用户选择了拒绝"。
  - **这是行业通用做法**，不是 AdSense 专属发明——网上常见的"我们使用 Cookie，接受/管理偏好"弹窗就是这个东西。
  - **自动化审查大概率是在查 `window.__tcfapi`**：IAB TCF 标准要求认证 CMP 在页面上暴露一个全局函数 `__tcfapi()`，供广告代码读取同意信号；Google 的自动扫描很可能就是在查这个函数存不存在，而不是解析隐私政策文字——这也解释了为什么"隐私政策里写了 AdSense 会用 Cookie"对这项检测完全没有影响。
- **儿童导向内容声明**（同样容易被漏掉）：隐私政策里要有清楚独立的"本站不面向 13 岁以下儿童"声明；AdSense 后台有单独的 child-directed 开关，只能由账号持有人确认。审查时要明确报告需要账号持有人确认。

## 如何在自己的项目里排查
- **广告接入点**：找到 `google-adsense-account` meta 标签和实际渲染广告的组件，确认每个广告位每页只渲染一次（改动后检查有没有变成渲染多次）。
- **内容深度排查**：抓 sitemap、抽样若干内页，统计**去壳后的**正文词数（去掉共用的 header/footer/nav/模板）。中位数低于约 500 词、或多页低于 250 词、或跨页共用"How to use"骨架，就是薄页信号——即便没有任何政策违规，也要按 High/Blocker 报告。
- **复制内容排查**：起一个真实的生产构建服务器（例如 `next build && next start`，或你所用框架的等价命令）验证，不要只看开发模式页面。真实抓取渲染后的 HTML，数一段独特正文在里面出现了几次；纯肉眼看页面会漏掉响应式断点各写一份、或被 CSS 隐藏的重复内容。用真实 HTTP 状态码验证，不要凭"页面看起来没问题"下结论。
- **客户端挂载的广告位**：如果广告组件是纯客户端渲染的（React/Next.js 里常见），广告 DOM（比如 Google 的 `ins.adsbygoogle`）只会在 **hydration 完成后**出现——查服务端渲染的原始 HTML 永远会显示 0 个广告元素，跟广告到底有没有正常工作没有关系。要在真实浏览器里等页面加载完再查，不要只 grep SSR 输出。
- **信任页**：检查首页页脚的 About / Contact / Privacy / Terms 链接是否都在且可用；链接指向占位页或 404 时不算通过。
- **CMP 和 child-directed 标记**：如果这两项账号层面的设置查不到，要如实说明，报告"需要账号持有人去后台确认"，不要因为"代码里看不到"就当成"没问题"。

## 工具无法核实、需站长自查的项（列成清单交给站长）
这些正是要交回给站长的"Unknown"项——逐项确认，不要替站长判通过/失败：
- ADS-ELIG-01/02 —— 是否成年、有无重复账号。
- ADS-OWN-01/02 —— 有无 `<head>` 注入权限、域名是否在自己名下。
- ADS-SITE-01/02 —— 是否已在后台添加站点、所有权验证方式可否部署。
- ADS-PROG-01 —— 绝不点自己的广告、绝不刷展示/点击。
- ADS-PROG-04 —— 流量来源合法（无 PTC/互点/垃圾邮件）。
- ADS-PROG-06 —— 广告只放内容页。
- ADS-PRIV-03 —— 广告请求不传 PII。
- ADS-PRIV-05 —— 收集定位须先取得同意（或不适用）。
- ADS-PRIV-06 —— 后台确认 child-directed 开关。
- ADS-PRIV-08/09/10 —— 不用敏感信息定向；美加房产/招聘/信贷规则；IBA 披露。

## 可选：没有 CMP 服务商账号时的过渡方案
部署经认证的 CMP 需要开通第三方服务商（Cookiebot/OneTrust 等）账号，或配置 Google 自家的 Privacy & messaging 页签——这两者都需要账号持有人本人登录，不是纯代码改动能完成的。如果想在此之前先降低风险（不能替代真正的合规要求，只是止损），有两个值得了解的做法：

1. **全局保守默认值**：在每次调用 `adsbygoogle.push({})` 之前，设置 `window.adsbygoogle.requestNonPersonalizedAds = 1`（官方文档见 [support.google.com/adsense/answer/9042142](https://support.google.com/adsense/answer/9042142)）。这会让整站在真正接入 CMP 之前默认只请求非个性化广告——收入会低一些，但不会出现"未经同意展示个性化广告"的问题。
2. **自建的、按地区判断的同意横幅**（依然不是认证 CMP——它本身不能让受限地区解锁个性化广告，代码注释里要明确写清楚这一点，避免以后审查的人把它误判成已经合规）：客户端用一个免费无需注册的 IP 地理位置接口判断访客是否在 EEA/英国/瑞士，结果本地缓存一段时间；只对命中这些地区的访客弹一个简单的接受/拒绝提示，选择存本地，并接入上面提到的 `requestNonPersonalizedAds` 判断逻辑。要给用户留一个之后能重新选择/清除这个选择的入口（比如 Cookie 政策页面上的一个按钮）。这个做法容易踩一个真实的 UI 坑：如果把横幅固定在页面顶部，很可能会跟站点本身固定定位的顶部导航栏叠在一起、互相遮挡（同样的 z-index、同样的 top:0）；固定在底部可以避开这个问题，也更符合大多数同意横幅（包括 Google 自家的 Funding Choices）的通行位置。
